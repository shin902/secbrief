# secbrief

[English](README.md) | **한국어** | [中文](README.zh.md) | [日本語](README.ja.md)

**AI 에이전트가 관리하는 머신을 위한 매일의 취약점 브리핑.**

"내 머신의 취약점을 지켜봐 줘"라고 AI 에이전트에게 부탁하세요. 에이전트가 이것을 설치합니다. 그 후로는 몇 시간마다 머신이 생성한 브리핑이 "무엇이 바뀌었는지", "어디에 당신의 판단이 필요한지"를 알려줍니다. LLM은 아무것도 결정하지 않습니다 — 설명만 합니다.

```bash
git clone <this repo> && cd secbrief
python3 secbrief.py init        # config.json 생성
$EDITOR config.json             # SSH 호스트 / python 환경 / brew 감시 목록
python3 secbrief.py run --baseline   # 첫 실행: 기준선 작성 (경보 없음)
python3 secbrief.py run              # 이후 cron/launchd로 6시간마다. 차분만 경보
python3 secbrief.py doctor           # 스캐너가 살아 있는가? 마지막 성공은 언제인가?
```

설치 시간은 약 5분. API 키도 계정도 에이전트 프레임워크도 필요 없습니다.

## 하는 일

**정보원 (무료 · 공식 · 키 불필요):**
- [OSV.dev](https://osv.dev) querybatch + 어드바이저리 상세 — 실제 설치된 버전과 대조 (PyPI는 purl, Ubuntu/Debian은 `pkg:deb/<distro>/...`). 시스템 패키지는 디스트로 어드바이저리가 진실이며, 백포트된 빌드(예: `1.1.0-2build2.1`)도 업스트림 버전 계산이 아니라 올바르게 판정됩니다.
- [CISA KEV](https://www.cisa.gov/known-exploited-vulnerabilities-catalog) — 실제로 악용되는 취약점은 격상. 이전에 "수락(accepted)"한 항목이라도 그 CVE가 나중에 KEV에 들어가면 **자동으로 수락 해제**됩니다.
- [formulae.brew.sh](https://formulae.brew.sh) — Homebrew에는 CVE 데이터베이스가 없으므로 포뮬러 버전 차이는 별도 섹션(업데이트 지연)으로 보고됩니다. 가짜 CVE로 취급하지 않습니다.

**인벤토리 (읽기 전용. 머신에 아무것도 변경하지 않음):**
- Python 환경: `pip list` (지정한 임의의 인터프리터)
- Ubuntu/Debian 호스트: SSH 경유의 `dpkg-query` (키 인증)
- macOS Homebrew: 감시 목록에 대한 `brew list --versions`

**브리핑** (markdown · 실행마다 1개 파일)은 모든 것을 다음 4분류로 정리합니다:

- `[要対応]` — fix가 공개되었고 CVE가 KEV 수재. 오늘 움직입니다.
- `[要対応（緩和）]` — 악용 중이지만 fix 미제공. 완화합니다 (입력 경로 차단).
- `[推奨]` — fix 공개 완료 · KEV 미수재. 자기 페이스로 적용.
- `[観察]` — fix 미제공 · 미악용. 지켜봅니다. (의도적으로 중요도 수치를 붙이지 않습니다: 패치 불가능한 버그에 대한 CVSS 점수는 노이즈이지 신호가 아닙니다.)
- 그 외에 머신이 무관하다고 증명한 `[不要]` 행, 확인 후 수락한 `[（accepted）]` 행, 그리고 brew 버전 차이 섹션.

모든 검출 행에는 기계 검증된 4점 조합(어드바이저리 ID · 도입 버전 · fix 버전 · KEV 표시)과 어드바이저리 링크가 붙습니다.

## 신뢰성을 지탱하는 규칙

1. **대조는 결정론적 코드로 하고 LLM으로 하지 않습니다.** 버전 비교는 환각이 실제 피해를 내는 곳이므로 모델에게는 일절 맡기지 않습니다.
2. **출력 게이트.** 어드바이저리 ID · 도입 버전 · fix 상태 · KEV 표시가 빠진 행은 출력할 수 없습니다 — 검증 불가능한 주장은 파기되어 집계됩니다. 검출 결과의 조작은 구조적으로 불가능.
3. **어드바이저리 본문은 데이터이지 지시가 아닙니다.** "이 커맨드를 실행하라"고 쓴 CVE 설명은 텍스트로 인용될 뿐. 설명 공정용 `PROMPT.md`도 같은 것을 LLM에게 명령합니다.
4. **워터마크는 전 소스 성공 시에만 진행됩니다.** 실패한 페치가 차분 상태를 진행시키면 미래의 CVE가 영원히 숨겨집니다. degraded 실행은 대신 `점검 실패` 경보를 냅니다. 조용히 죽은 스캐너는 안전해 보입니다 — 이 스캐너는 침묵하지 않습니다.
5. **첫 실행은 베이스라인.** 200개의 경보가 아니라 깨끗한 상태에서 시작합니다.
6. **"입력 경로가 없다"는 것을 기계가 결정하지 않습니다.** `ignore_overrides`에 등록할 수 있는 것은 당신뿐입니다. (기계가 증명할 수 있는 두 기계적 조건 — 디스트로 fix 완료 · 미인스톨 — 은 별도.)

## 두 가지 사용법

- **루트 A (LLM이 설명):** cron으로 secbrief를 돌립니다. 경보 파일이 갱신되면 `briefing.md`를 열거나 `python3 secbrief.py paste`로 PROMPT.md+브리핑 1개 파일을 만들어 임의의 LLM 채팅에 붙여 넣어 쉬운 설명과 우선순위가 붙은 계획을 내게 합니다.
- **루트 B (에이전트가 유지보수):** 코딩 에이전트에게 `AGENTS.md`를 넘깁니다. 설치 · 스케줄 · 생사 확인 · 패치 커맨드 초안 작성이 가능합니다. 그래도 무인 패치 적용은 하지 않습니다 — 당신이 "해줘"라고 말하고 직접 실행합니다.

## 스케줄링

6시간마다가 좋은 기본값 (12/24시간도 가능). launchd plist와 cron 행의 예는 `docs/scheduling.md`에 있습니다. 생사 확인은 `secbrief.py doctor` — 브리핑의 mtime이 주기의 2배보다 오래되면 작업이 죽은 것입니다.

## 정직한 한계

- 의도적으로 감시하지 않는 것 (분기마다 재검토): 컨테이너 이미지, 브라우저, EOL 런타임, snap/flatpak, 글로벌 npm 패키지. 브리핑 헤더에 매번 나열되므로 "보고 있지 않다"는 것을 잊을 수 없습니다.
- **OSV querybatch는 쿼리당 1,000건으로 잘립니다.** 그것을 넘는 소스(전형적으로 Linux 커널)에서는 API가 돌려주는 부분 집합이 불규칙하므로 secbrief는 열거를 포기합니다. 그 소스들은 디스트로 자신의 보류 업데이트 상태(apt 후보 = fix 있음)로 판정한 1행으로 압축되고 헤더에 이름이 실립니다(`OSV 1000-cap`). 그것들에 대한 CVE 단위의 KEV 격상은 불가능 — 단, 대응 액션(distro 업데이트 실행)은 변하지 않습니다.
- 정보원 지연: OSV는 빠르지만(보통 24시간 이내) 즉시는 아닙니다. CISA KEV 카탈로그는 미국 정부의 스케줄로 갱신됩니다.
- 브리핑은 "무엇을 고쳐야 하는가"를 전하지만, 당신의 특정 앱을 안전하게 고치는 "방법"까지는 전하지 않습니다. fix 버전은 기계 검증 완료. 롤백 계획은 다릅니다.
- 이것은 브리핑 도구이지 스캐너 제품이 아닙니다: 패키지 인벤토리와 어드바이저리를 대조할 뿐. 런타임의 노출(어느 서비스가 실제로 신뢰할 수 없는 입력을 파싱하는가)은 보이지 않습니다 — 그 판단은 당신에게 남습니다.
- 가독성: `[要対応]`은 어드바이저리 단위 행을 유지. 큰 `[推奨]`/`[観察]` 백로그는 (패키지 × fix 상태) 단위로 압축하고 어드바이저리 ID는 모두 행 안에 남깁니다. `apt upgrade` 1회로 일괄 해소되기 때문입니다.

## 보안에 관하여

`SECURITY.md`를 참고하세요 (이 도구가 하는 일과 의도적으로 하지 않는 일 · 보고 정책). 비밀정보를 `config.json`에 두지 마세요. `.gitignore`에는 `config.json`, `state/`, `cache/`, `alerts/`가 처음부터 들어 있습니다.
