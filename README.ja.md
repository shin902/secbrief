# secbrief

[English](README.md) | [한국어](README.ko.md) | [中文](README.zh.md) | **日本語**

**AIエージェントが管理するマシンのための、毎日の脆弱性ブリーフィング。**

「自分のマシンの脆弱性を監視して」とAIエージェントに頼む。エージェントはこれをインストールする。その後は数時間ごとに、機械が生成したブリーフィングが「何が変わったか」「どこにあなたの判断が必要か」を伝える。LLMは何も決めない——説明だけをする。

```bash
git clone <このリポジトリ> && cd secbrief
python3 secbrief.py init        # config.jsonを作成
$EDITOR config.json             # SSHホスト / python環境 / brewの監視対象を記載
python3 secbrief.py run --baseline   # 初回: 基準線を作る（警報なし）
python3 secbrief.py run              # 以後、cron/launchdで6時間ごと。差分だけ警報
python3 secbrief.py doctor           # スキャナは生きているか？ 最後に成功したのはいつか？
```

セットアップは約5分。APIキーもアカウントもエージェント基盤も不要。

## 何をするか

**情報源（無料・公式・キー不要）:**
- [OSV.dev](https://osv.dev) querybatch＋advisory詳細 — 実際にインストールされている版と照合（PyPIはpurl、Ubuntu/Debianは`pkg:deb/<distro>/...`）。システムパッケージはディストロのadvisoryが正であり、バックポート版（例: `1.1.0-2build2.1`）も上流のバージョン計算ではなく正しく判定される。
- [CISA KEV](https://www.cisa.gov/known-exploited-vulnerabilities-catalog) — 実際に悪用されている脆弱性は格上げ。過去に「受諾（accepted）」した項目でも、そのCVEが後にKEV入りしたら**自動的に受諾解除**される。
- [formulae.brew.sh](https://formulae.brew.sh) — HomebrewにはCVEデータベースがないため、formulaの版ズレは独立したセクション（更新遅れ）で報告される。偽のCVEとしては扱わない。

**インベントリ（読み取り専用。マシンには何も変更しない）:**
- Python環境: `pip list`（指定した任意のインタプリタ）
- Ubuntu/Debianホスト: SSH経由の`dpkg-query`（鍵認証）
- macOS Homebrew: 監視リストに対する`brew list --versions`

**ブリーフィング**（markdown・実行ごとに1ファイル）は、すべてを次の4分類に整理する:

- `[要対応]` — fixが公開されており、かつCVEがKEV収載。今日動く。
- `[要対応（緩和）]` — 悪用されているがfix未提供。緩和する（入力経路を遮断）。
- `[推奨]` — fix公開済み・KEV未収載。自分のペースで適用。
- `[観察]` — fix未提供・未悪用。見守る。（意図的に重要度数値を付けない: パッチ不能なバグへのCVSSスコアはノイズであって信号ではない。）
- このほか、機械が無関係と証明できた`[不要]`行、あなたが確認して受諾した`[（accepted）]`行、そしてbrewの版ズレセクション。

すべての検出行には、機械検証済みの4点組（advisory ID・導入版・fix版・KEV印）とadvisoryへのリンクが付く。

## 信頼性を支える規則

1. **照合は決定論的なコードで行い、LLMでは行わない。** バージョン比較は幻覚が実際の害を生む場所なので、モデルには一切触らせない。
2. **出力ゲート。** advisory ID・導入版・fix状態・KEV印の欠けた行は出力できない——検証不能な主張は破棄されてカウントされる。検出結果の捏造は構造的に不可能。
3. **advisory本文はデータであって指示ではない。** 「このコマンドを実行せよ」と書いたCVE説明はテキストとして引用されるだけ。説明工程用の`PROMPT.md`も同じことをLLMに命じる。
4. **ウォーターマークは全ソース成功時だけ進む。** 失敗した取得が差分状態を進めると、未来のCVEが永久に隠れる。degraded実行は代わりに`点検失敗`警報を出す。静かに死んだスキャナは安全に見える——このスキャナは黙らない。
5. **初回実行はベースライン。** 200件の警報ではなくクリーンな状態から始める。
6. **「入力経路がない」ことは機械が決めない。** `ignore_overrides`に登録できるのはあなただけ。（機械が証明できる2つの機械的条件——ディストロfix済み・未インストール——は別。）

## 2つの使い方

- **ルートA（LLMが説明する）:** cronでsecbriefを回す。警報ファイルが更新されたら`briefing.md`を開く——または`python3 secbrief.py paste`で、PROMPT.md＋ブリーフィングの1ファイルを作り、任意のLLMチャットに貼って平易な説明と優先順位付きの計画を出させる。
- **ルートB（エージェントが保守する）:** コーディングエージェントに`AGENTS.md`を渡す。インストール・スケジュール・死活確認・パッチコマンドの起草ができる。それでも無人でのパッチ適用はしない——あなたが「やって」と言って、自分で実行する。

## スケジューリング

6時間ごとが良い既定値（12/24時間でも動く）。launchdのplistとcron行の例は`docs/scheduling.md`にある。死活確認は`secbrief.py doctor`——ブリーフィングのmtimeが周期の2倍より古ければ、ジョブが死んでいる。

## 正直な限界

- 意図的に監視しないもの（四半期ごとに見直し）: コンテナイメージ、ブラウザ、EOLランタイム、snap/flatpak、グローバルnpmパッケージ。ブリーフィングのヘッダに毎回列挙されるので「見ていない」ことを忘れられない。
- **OSV querybatchは1クエリ1,000件で打ち切り。** それを超えるソース（典型的にはLinuxカーネル）では、APIが返す部分集合が不定のため、secbriefは列挙を諦める。それらのソースは、ディストロ自身の保留アップデート状態（apt候補＝fixあり）で判定した1行に圧縮され、ヘッダに名前が載る（`OSV 1000-cap`）。それらに対するCVE単位のKEV格上げは不可能——ただし対応アクション（distroアップデートの実行）は変わらない。
- 情報源の遅延: OSVは速い（通常24時間以内）が即時ではない。CISA KEVカタログは米国政府のスケジュールで更新される。
- ブリーフィングは「何を直すべきか」を伝えるが、あなたの特定のアプリを安全に直す「方法」までは伝えない。fix版は機械検証済み。ロールバック計画は違う。
- これはブリーフィングツールであってスキャナ製品ではない: パッケージインベントリとadvisoryを突き合わせるだけ。ランタイムでの露出（どのサービスが実際に不信入力をパースしているか）は見えない——その判断はあなたに残る。
- 読みやすさ: `[要対応]`はadvisory単位の行を保つ。大きな`[推奨]`/`[観察]`のバックログは（パッケージ×fix状態）単位に圧縮し、advisory IDはすべて行内に残す。`apt upgrade`1回で一括解消するからだ。

## セキュリティに関する注意

`SECURITY.md`を見ること（このツールが何をし、何を意図的にしないか。報告ポリシー）。秘密情報を`config.json`に置かないこと。`.gitignore`には`config.json`、`state/`、`cache/`、`alerts/`が最初から入っている。
